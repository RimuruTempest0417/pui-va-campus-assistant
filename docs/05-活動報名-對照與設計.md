# W-17 活動報名進階：舊項目對照與本項目設計

> 借鑒對象：Gary 早前的 `competition-manager`（技術到位、UI 不合格）。
> 原則：**只搬流程與資料模型，版面一律回到本項目的 design tokens。**

## 一、舊項目怎麼做 vs 本項目怎麼做

| 能力 | competition-manager 的做法 | 本項目（W-17） | 為什麼不同 |
|---|---|---|---|
| 名額與剩餘 | 欄位 `capacity` ＋ 每次查詢時 `count(*)` 現算 | 後端交易內 `SELECT … FOR UPDATE` 鎖活動列；`signedCount` 由報名列統計，回傳 `remaining` | 舊做法在併發下會超賣；本專案已有 20 併發壓測 |
| 候補 | 有 `waitlist_order` 表，手動調整順序 | `EventSignup.waitlistPos`，取消自動補位＋重排 | 少一張表，順位就是資料的一部分，不會與狀態脫節 |
| 批次操作 | 後台表格勾選 → 逐筆 API | `PATCH /admin/events/:id/signups/batch`：`PROMOTE_ALL`（補到上限）／`CANCEL`（指定 ids） | 一次交易做完，避免「轉 10 個人、第 7 個失敗」這種半成品狀態 |
| 統計 | 一整頁報表（表格塞滿） | 活動卡上按「統計」→ 四個數字＋7 天趨勢，**不開新頁** | 舊版面資訊密度過高；本項目首屏可點元素 ≤ 6 的規則優先 |
| 分組 | 報名表單就有組別、隊伍、指導老師等十幾個欄位 | 第一階段**不做**分組欄位；先做統計與批次（真的需要再加 `groupKey`） | 欄位加上去會讓報名表單變長，沒有實際需求前不加 |
| 匯出 | CSV（全班級全欄位） | 保留既有 `/admin/events/:id/signups.csv`（UTF-8 BOM） | 桌面端才做，小程序不做下載 |

## 二、本項目這一階段的範圍（v0.20.0 / 後端 v0.9.0）

### 後端

```
GET  /api/v1/events/:id/stats          event:create（老師只能看自己開的）
PATCH /api/v1/admin/events/:id/signups/batch   { action: 'PROMOTE_ALL' | 'CANCEL', ids?: [] }
```

回應長相：

```json
{
  "eventId": "…", "capacity": 30, "unlimited": false,
  "signed": 27, "waitlisted": 8, "cancelled": 1, "remaining": 3, "full": false,
  "waitlist": { "count": 8, "firstPos": 1, "lastPos": 8 },
  "timeline": [{ "date": "2026-10-17", "count": 2 }, "…7 天"]
}
```

規則：
1. `PROMOTE_ALL` 只補到**名額上限**，不是全部轉正（`capacity = 0` 才全轉）
2. 轉正後**重排剩餘候補**，不留空洞
3. 交易內 `FOR UPDATE`，與同時報名互斥
4. 被轉正者發訂閱消息（有同意才發）

### 前端

- 後台「活動」分頁：每張活動卡多一顆**統計**按鈕 → 卡上方出現統計卡（正取／候補／剩餘／取消＋7 天趨勢）＋「候補全部轉正」
- 統計卡「收起」即回復列表，不跳頁

## 四、下一階段（未做，列在規劃書）

## 五、第二階段：分組（v0.28.0／後端 v0.14.0）

| 能力 | competition-manager | 本項目 |
|---|---|---|
| 組別資料 | 另外開 `teams` 表，含隊長、指導老師、成員 | `Event.groups`（Json 陣列）＋`EventSignup.groupKey` |
| 報名時選組 | 報名表單十幾個欄位 | 詳情頁 chips，未選不能送出（後端也擋） |
| 各組名額 | 有 | **不做**（名額活動層級共用） |
| 統計 | 另開報表頁 | 後台統計卡直接列各組正取／候補／出席 |
| 匯出 | CSV 全欄位 | CSV 多一欄「組別」 |

刻意不做：隊伍／隊長／指導老師。校內分組的實際需求是「按班別或程度分兩三組」，
加上成員管理會讓報名從 2 步變成 8 步，與本項目「首屏可點元素 ≤ 6」的規則衝突。
