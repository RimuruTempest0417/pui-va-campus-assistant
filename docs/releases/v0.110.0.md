# v0.110.0 — 全校搜尋補上功課與提案：記得「上星期那份三角函數」就找得到（2026-11-07）

任務：W-91（前端 v0.110.0／後端 v0.63.0）

## 為什麼做這一項

全校搜尋（W-59）上線時只搜五類：公告、活動、失物、轉贈、菜單。後來新增的**功課**（W-76）與
**校園提案**（W-88）沒有接進來，於是出現一個很日常的落差：學生記得「上星期有一份關於三角函數的功課」，
卻只能一頁一頁翻功課清單；同學想找回「之前有人提過的圖書館建議」，也只能在提案列表裡滑。
資料本來就在，缺的只是搜尋入口 —— 這就是這一版補的洞。

## 做了什麼

### 後端（v0.63.0）

- **`GET /search` 多兩組**：`types` 新增 `homework`／`proposal`（預設七類全搜，原本五類行為不變）：

  | 類別 | 可見規則 | `badge` | `date` | 額外欄位 |
  |---|---|---|---|---|
  | `homework` | **只搜自己那一班**（班級取自 JWT 對應的使用者，前端不能指定別班）、排除軟刪除 | 科目 | 截止時間（排序由近到遠） | `className` |
  | `proposal` | 排除軟刪除（撤回／下架），**「暫不採納」仍然回** | `category:status` | 提出時間 | `supportCount`／`goal` |

- **功課的班級判斷與 `GET /homework` 同一條**：`can(role, 'homework:read')` 先過能力，
  再用 `User.className` 查 —— 未登入、家長、沒有設定班級的學生**連這一組都不會出現**
  （不是回一組空陣列，前端就不會多一個「功課 0」的分類標題）。
- **提案的 `DECLINED` 刻意留著**：同學要知道「提過但沒做」，那本身就是資訊；只有撤回／下架（軟刪除）不算。
- `SearchHit` 型別多三個選填欄位（`className`／`supportCount`／`goal`），前端不必為了顯示
  「連署 3 / 20」再打一支端點。
- **沒有新表、沒有 migration**。e2e `search.test.ts` 新增 **2 項**（14 → 16）：
  - 功課只搜自己班（別班、已收回、未登入、家長、沒設班級五種情況一次驗完）；
  - 提案撤回的搜不到、暫不採納仍搜得到、`badge` 是「分類:狀態」、訪客也有這一組但沒有功課那一組。

### 前端

- **搜尋頁（`pages/search`）**：
  - 類型 chips 從 6 個（全部＋五類）變成 8 個（全部＋七類），沿用既有的 `flex-wrap` 排法，不改成橫向捲動；
  - **「功課」chip 依角色給**：讀到角色後只有學生以上才出現（後端 `homework:read` 的鏡像），
    訪客與家長不會看到一顆「點下去永遠沒有結果」的 chip；切到功課後才發現沒權限時會自動回到「全部」；
  - 每組結果的徽章與時間依類別給：功課＝「科目」＋「截止 11月08日 23:59」、提案＝「校園設施 · 校方處理中」＋「連署 3 / 20 · 3 天前」；
  - 提案的分類／狀態文字走 `utils/proposal.js`（`categoryLabel`／`statusLabel`／`statusTag`），不另抄一份對照表；
  - **跳轉**：提案跳詳情頁；功課**不接 id**（功課只有一頁清單＋打勾），新增 `NEEDS_ID` 對照表處理這種「不吃 id 的類別」。
- **示範層（`services/mock.js`）同一套規則**：功課用「年級＋班」組出的班級、家長與訪客不出現這一組；
  提案票數一律由 `supporters` 陣列長度算（不讀 `supportCount`，避免兩份數字對不上）。
- **使用說明補兩處**：訪客分頁「想找一則舊公告…」與學生分頁「怎麼一次找公告、活動、失物？」
  都改寫成七類，並寫清楚「功課只搜自己班、要登入」與「提案連暫不採納都留著」。
- `docs/openapi.yaml`：`/search` 的說明、`types` 參數、`groups[].type` enum 與 `SearchHit` schema 一起更新
  （190 路徑／232 操作，parity 兩邊 0 落差）。

## 抓到的問題（邊做邊修）

- **`SearchHit.type` 的 enum 與 `parseTypes` 是兩份手抄清單**：改成一組 `ALL_TYPES` 常數同時餵型別與驗證，
  否則以後再加一類一定有一邊忘了改。
- **`date` 對功課是最容易寫錯的排序**：照抄其他類別的「新到舊」會讓「下週才交」排在「明天要交」前面，
  功課改成「截止時間由近到遠」（標題命中仍然優先）。
- **`check-data-layer` 第一版的「已撤回提案不出現」是假檢查**：示範資料裡沒有撤回的提案，
  斷言永遠成立。改成檢查示範層真的帶 `!p.deletedAt` 過濾與票數來源，避免這種「看起來驗了」的守門。

## 設計取捨

- **不另開一支 `/search/homework`**：搜尋的價值在「一次打完就看到全部」，拆成多支等於要前端併多次請求；
  而且可見性規則留在原本的地方（公告用 `visibleNoticeWhere`、功課用班級、提案用 `deletedAt`），
  沒有第二份真相。
- **功課不加「已交／未交」狀態**：搜尋結果是「找到那一則」，打勾狀態屬功課頁；
  塞進來會讓搜尋多做一次 `HomeworkDone` 查詢，而且使用者點進去就看到，不必在搜尋列上重複。
- **提案顯示連署進度而不是只顯示狀態**：校方回覆前，「有沒有達標」才是同學關心的；
  `supportCount`／`goal` 直接跟著 hit 回，前端不用為此再打一支詳情。
- **訪客也能搜到提案、但搜不到功課**：這是能力矩陣既有的結論（`proposal:read` 在 GUEST 裡、
  `homework:read` 要登入），搜尋只是照著它走，沒有另外發明規則。
