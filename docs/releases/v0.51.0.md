# v0.51.0 — 編輯衝突保護：後存的人不再靜默蓋掉前一位（W-42）

日期：2026-10-25

## 為什麼

同一個活動或同一則公告，兩位老師幾乎同時在後台動手時，**後按下去的那一次會直接蓋掉前一位的修改**：
沒有任何提示、資料就變了、前一位也不會知道。校內同時有資訊管理員與老師在動同一批內容，這不是理論風險。

上一版把「誰能改什麼」管住了（權限矩陣），這一版管的是**同一份資料被兩雙手的時間差**。

## 改動

| 檔案 | 改什麼 |
|---|---|
| `pages/admin/index/index.wxml` | 「置頂／取消置頂」「取消／恢復活動」兩顆按鈕多帶 `data-version="{{item.version}}"`（清單回來的版本） |
| `pages/admin/index/index.js` | 新增 `versionPatch(dataset)`（dataset 是字串，只有真的是數字才放進 payload）與 `onWriteError(err, reload)`；兩個 handler 改成帶 `version`，收到 **409 `CONFLICT`** 時彈「這筆剛被別人改過」＋**自動重抓清單** |
| `services/admin.js` | 不用改：`updateNotice`／`updateEvent` 本來就整包 payload 轉發 |
| `scripts/check-project.mjs` | 新增第 18 條守門：`pages/` 底下每一處 `admin.updateNotice()`／`admin.updateEvent()` 呼叫都必須帶 `version` |
| `utils/i18n-phrases.js` | 重建對照表（796 組，新增「這筆剛被別人改過」「你看到的不是最新版本…」兩句） |
| `docs/openapi.yaml` | `Notice`／`Event` 加 `version`；`PATCH /admin/notices/{id}`、`PATCH /admin/events/{id}` 補 requestBody 與 `409` |

後端（`pui-va-campus-server` v0.26.0）才是鎖的所在：`Notice`／`Event` 各加 `version Int @default(0)`，
比對寫在**同一條 UPDATE 的 WHERE**（`WHERE id = ? AND version = ?` ＋ `SET version = version + 1`），
不是「先讀再比再寫」——後者在兩人同時存檔時仍會雙寫成功，等於白做。

## 抓到的坑

- **守門寫太嚴會把自己的正確寫法判成錯**：第一版規則只認 `\bversion\b`，而我們的寫法是 `...versionPatch(dataset)`，
  單字邊界在 `versionPatch` 裡不成立 → 兩處正確的呼叫被報錯。改成 `\bversion(Patch)?\b` 才對。
  記住：**守門紅燈要先確認是程式錯還是規則錯**，直接改程式去迎合規則會寫出更差的程式。
- **改到含 `?? ''`、`${}` 的行要 `node --check`**：這一版 `index.js` 動到好幾段既有邏輯，patch 後立即跑
  `check-project`（內含全 `.js` 的語法檢查）確認沒有留下字串殘骸 —— 這支檔一壞，整個後台會變空白頁。

## 設計取捨

- **不帶 `version` 一律放行**：舊版小程序、curl、其他工具都還在打同一支端點，硬性要求會讓它們全部 412。
  代價是「忘了帶」的那條路徑保護不到，所以用守門第 18 條把前端所有呼叫端釘住（後端不可能分辨「舊客戶端」與「忘了帶」）。
- **409 之後不自動重送**：自動重送就等於讓後存的人贏 —— 那正是這道鎖要擋的事。只提示＋重新載入，讓人自己看過再決定。
- **網頁後台這版沒有要改的地方**：它目前對公告只有「新增」、對活動只有「匯出 CSV」，沒有編輯動作，
  所以不存在衝突面；等之後網頁後台加上編輯表單時，同一個 `version` 欄位直接沿用（契約已在 openapi 裡）。
