# v0.75.0 — 可以先寫好，明早八點才出現（W-58 公告預約發佈）

後端對應版本 **v0.36.0**。

## 做什麼

老師最常遇到的情境是這樣：星期五放學前想把「下週一升旗改在禮堂」寫好，
但星期五傍晚發出去，整個週末沒人會看，星期一早上又忘了再發一次。
或是活動報名週一 08:00 才開放，公告卻得在 07:00 手動按下去。

這一版讓公告**可以預約**：

- 後台「公告」分頁多一條「發佈時間（留空＝立即發佈）」：選日期 → 自動補 08:00 → 可再改時間。
- 按發布後：**到那個時間之前，學生與家長完全看不到**（列表沒有、直接點網址也是 404），
  但老師的後台看得到，標成「排程中 · 10/27（一）08:00」。
- 想提前就按該列的「**立即發佈**」，公告馬上出現（不用刪掉重發）。
- 網頁後台 `/admin` 同一套（發佈時間欄位、清單標「（排程中）」、同一個「立即發佈」按鈕）。

## 三條刻意的規則

1. **緊急公告不能預約**（422）。緊急公告的價值在於「立刻推播給已訂閱的人」，
   而排到未來的公告在時間到的那一刻**不會有任何推送**（沒有東西去觸發）——
   結果會是一則「紅色標籤但沒人知道」的公告，比不發更糟。
2. **最多預約 90 天**。老師選年份少按一位（2026 → 2062）的話，那則公告永遠不會出現，
   而後台只顯示「排程中」，查起來非常痛苦。
3. **可見規則只有一份**：`src/routes/notices.ts` 的 `visibleNoticeWhere(now)`
   （沒刪、已到時間、沒過期）同時給公開列表、詳情頁、「全部標為已讀」、後台概況、
   家長端的子女概況使用。原本家長端自己抄了一份（已含 `publishedAt`），
   而公開列表沒有 —— 這種「兩份規則」遲早會出現「家長看得到、學生看不到」的鬼故事。

## 設計取捨

- **不加排程器（cron／queue）**：可見性靠查詢條件 `publishedAt <= now` 判斷，
  時間一到自然就出現，不需要「時間到去把某個欄位打開」的背景工作 ——
  少一個會壞掉的零件，也不會出現「排程沒跑，公告卡住」的狀態。
- **不加資料表欄位**：`Notice.publishedAt` 本來就有（預設 `now`），這一版只是開始讓它可以是未來。
  代價是「排程中的公告」與「已發佈的公告」在資料庫裡長得一樣，只能靠時間判斷（可接受）。
- **緊急公告選擇擋掉而不是「允許但到時間再推」**：後者要記住「這則還沒推過」，
  又是一次 schema 變更＋一支定時任務；現階段的取捨是「先支援一般與校曆公告的預約」。

## 已知缺口

- 預約的公告**不會發微信訂閱消息**（本來就只有緊急公告會推，而緊急不能預約）。
- 排程的公告不會自動置頂排序；置頂仍是手動開關。
- 小程序後台的日期／時間選擇器只驗到資料與邏輯（`publishAtISO()` 產出的 UTC 值），
  **實際 picker 的操作手感沒有親眼驗**。
