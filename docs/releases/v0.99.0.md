# v0.99.0 — `/health` 的版本號終於可信（W-80，後端 v0.53.1；前端只改版號）

任務：W-80（前端 v0.99.0；後端 v0.53.1）

## 這一版在回答什麼問題

每次發版都要回答一句「線上跑的到底是哪一版」。以前唯一的辦法是去看 Vercel 的部署 commit，
而 Vercel 又會因為 commit 作者不是連結帳號而回 `BLOCKED`、或停在舊版 —— 於是「部署驗證」這件事
一直靠一個不可靠的間接證據。

`/health` 本來就有 `version` 欄位，但它**硬編 `0.1.0`**（從第一版就沒再改過），
所以每次 `curl /health` 看到的都是同一個假答案。這一版把它改成讀 `package.json`，
版本號只剩一個來源；順手讓 `check:drift` 拿線上 `/health` 的版號跟本機 `package.json` 比對，
「線上是不是新版」從猜變成一行指令的答案。

## 改了什麼（後端 `pui-va-campus-server` v0.53.1）

- `src/routes/health.ts`：`readVersion()` 從 `import.meta.url` 往上兩層讀 `package.json` 的 `version`，
  在建置前（`src/routes/` → tsx）與建置後（`dist/routes/` → node）都指向同一個檔；
  **讀不到時回 `unknown`，不退回硬編版號**（退回去就等於再次開始漂）。
- `tests/e2e/health.test.ts`（新檔，3 項）：`/health` 的 `version` 等於 `package.json`、
  不得再是 `0.1.0`、必須是 `x.y.z` 形狀（部署腳本與 release note 是直接比字串）。
- `scripts/check-prod-drift.mjs`：`[2/4] 線上健康` 多一條「`/health` 版號等於本機 `package.json`」，
  失敗時直接說明「`0.1.0` ＝ 線上還是硬編版的舊部署」。
- `docs/04-端點實作清單.md`：`/health` 那列補上「版本號讀 `package.json`」。

## 設計取捨（答辯會被問的）

- **不用 `import pkg from '../package.json'`**：`tsconfig` 的 `rootDir` 是 `src`，把 `src` 外的 JSON
  拉進編譯會讓輸出目錄結構變形（`dist/src/...`），連帶所有相對路徑與 `start` 腳本都要改。
  用 `readFileSync(join(dirname(import.meta.url), '..', '..', 'package.json'))` 兩層就到專案根，
  建置前後一致，也不必開 `resolveJsonModule` 的副作用。
- **不加 `/health` 的 git commit 欄位**：Vercel 有 `VERCEL_GIT_COMMIT_SHA`，但本機與容器沒有，
  會變成「線上測得到、本機測不到」的分支。commit 由 `check:drift` 的 Vercel API 那一節負責。
- **前端這一版只改 `config/config.js` 的 `VERSION`**：功能沒有動，所以不重新上傳、不合 `main`。

  換版前是 `0.1.0`，約 80 秒後變 **`0.53.1`** —— 這正是這一版要解決的那件事，用同一個數字證明。
