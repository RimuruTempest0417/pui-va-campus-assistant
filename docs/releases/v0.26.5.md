# v0.26.5 — 顏色只剩一個來源：硬編碼色清零＋網頁後台換回培華紫（2026-10-25）

## 為什麼

設計規範第一句就寫「頁面與組件只准用變數，不要寫死色值」，但實際 grep 還有一批 `#fff`、`#ffffff`、
`rgba(0,0,0,…)` 散在 12 個檔案裡；後台（小程序與網頁）的 `switch` 還留著**上一版綠色系的 `#17694a`**，
網頁後台 `GET /admin` 整套更是綠的（`--brand: #17694a`）。使用者看兩個後台會覺得「像兩套系統」。
硬編碼色不清掉，之後要做深色模式時每一個寫死的 `#fff` 都是一顆地雷（深色底上會變白底白字），
所以這輪先把「顏色只有一個來源」變成**可被腳本擋下來的規則**，而不是靠記得。

### 新增的三條守門

1. **不得寫死色值**：掃 `pages/`、`components/`、`styles/`、`utils/`、`services/` 的 `.wxss`／`.wxml`／`.js`，
   命中 hex 或 `rgb(a)` 就報錯（例外：`tokens.wxss`、`style-guide` 展示頁、`utils/theme.js`）。
2. **CSS 變數必須先定義**：用到 `tokens.wxss` 沒有的 `--pv-*` 直接報錯 —— 這種錯不會讓編譯失敗，
   只會靜默退回繼承色，畫面看起來「顏色怪怪的」而 console 全綠。
3. **`utils/theme.js` 與 tokens 必須一致**：`tint`／`brand`／`danger`／`onTint` 四個值逐字比對，避免兩份真相。

## 抓到的真 bug（第 2 條守門一加就現形）

四個變數**從來沒定義過**，一直是靜默失效：

| 位置 | 用了 | 實際結果 | 修正 |

| `pages/menu/dish` 星評 | `--pv-accent` | 星形永遠是灰的（`is-on` 沒生效） | 新增 `--pv-accent: #e0a100` |

## 取捨

- **沒有直接做深色模式**：`@media (prefers-color-scheme: dark)` 在 Skyline 的行為還沒實測（設計規範「已知偏離」已記錄
  `prefers-reduced-motion` 同類風險），貿然把 `page` 的底色翻黑，19 頁裡只要有一頁還有寫死的白底就是白底白字。
  這輪先把「顏色只有一個來源」與守門做完 —— 那是深色模式的前置條件；真正的深色主題另開一項，等能在真機確認 Skyline 的 media query 再動。
- **`--pv-on-tint` 而不是直接寫 `#fff`**：白字在紫底、紅底上是同一個白，但它屬於「前景」而不是「表面」，
  分成語意 token 之後，將來深色模式只需要改這一顆，不用回頭找 40 處 `color: #fff`。
- **網頁後台的 `--ink` 系列沒有改成純黑**：網頁是長時間打字的桌面介面，`#14181a` 比 `#000` 柔和；
  小程序的 `--pv-label` 維持 `#000`（iOS 規範）。兩邊共用的是**品牌色與語意色**，不是所有中性色。
- 網頁後台的 `--brand` 直接寫死 `#6d3fc4`（不與小程序共用檔案，因為不同 repo、不同建置）：
  靠 `tests/admin-ui.test.ts` 守門 —— 色值只准出現在 `:root`，且舊綠色 `#17694a` 一出現就紅。
