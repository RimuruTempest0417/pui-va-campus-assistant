# v0.108.0 — 課室設備報修：壞掉的東西有單可追（2026-11-07）

任務：W-89（前端 v0.108.0／後端 v0.61.0）

## 為什麼做這一項

前十二項功能都在解決「學生要辦的事」（借書、借場地、請假、交功課、提建議），
但校園裡最常發生的一件事反而完全在系統外：**課室的冷氣滴水、投影機沒訊號、門鎖壞了**，
現在只能口頭跟班主任講。總務不知道哪一間最急、也沒有人記得修好了沒。

這一版把它變成有狀態的單子：學生報一次 → 總務接單（誰先按誰拿到）→ 修好寫備註 →
報修人在兩個時間點都收到站內通知。與「場地借用」互補：一個是借出去用，一個是壞了要修。

## 做了什麼

### 後端（v0.61.0）

- **一張新表**（第 36 支 migration）：`repair_requests` —— 地點、設備、說明、急迫度
  （`LOW`／`NORMAL`／`HIGH`）、狀態（`PENDING`→`IN_PROGRESS`→`DONE`，另有 `CANCELLED`）、
  報修人、處理人、接單時間、完成時間、處理備註、`version`；三個索引（狀態＋急迫度＋時間、報修人、地點）。
- **8 支端點**：
  - `POST /repairs`（送出；照片只收 http(s)，非 http 回 422）
  - `GET /repairs/mine`（我的報修＋進行中／已完成數）、`GET /repairs/:id`（報修人或總務）
  - `DELETE /repairs/:id`（只有送出者、只有待接單時可以取消）
  - `GET /admin/repairs`（待接單按「急迫度→送出時間」排序，其他按更新時間；回 `counts`）
  - `POST /admin/repairs/:id/accept`、`POST /admin/repairs/:id/done`
  - `GET /admin/repairs/stats`（各狀態、平均處理時數、近 7 天每日新增、報修最多的前 10 個地點）
- **接單是「誰先按誰拿到」**：`updateMany({ where: { id, status: 'PENDING' } })`，兩個同事同時按時只有一次成功，
  另一個人回 **409**，不是靜默覆蓋處理人。完成同樣是條件式更新（只能從 `IN_PROGRESS`）。
- **通知三段都接上**：送出時通知所有總務與管理員；接單、完成各通知報修人一次（含處理備註）。
  `NotifyKind` 新增 `REPAIR`，通知中心顯示「報修」標籤。
- **權限**：新增兩個能力 —— `repair:create`（學生以上；家長沒有）與 `repair:handle`（校內職員／管理員；
  **老師沒有**，老師只負責報修，接單是總務的事）。單調性維持：`ADMIN` 顯式帶上 `repair:handle` 才涵蓋 STAFF。
- 備份：`BACKUP_TABLES` 補 `repairRequest`，`backup.test.ts` seed 一列（報修人與處理人都要有）。

### 前端

- **兩個新頁面（第 46–47 頁）**：
  - `pages/repair/index`：分「處理中」（待接單＋已接單）與「已處理」兩組；每一列是「地點 · 設備」、
    急迫度與狀態標籤、送出時間、說明、處理人與備註；待接單的可以在原位取消。右上角膠囊「報修」。
  - `pages/repair/create`：在哪裡（常用地點 chips＋可自己打）、壞了什麼（七個 chips）、有多急（可以等／一般／急）、
    怎麼壞（textarea）、照片連結（選填，只收 https）。
- **首頁第九條入口列「課室報修」**：副標直接寫「N 張處理中」；新畫一個扳手線性圖標（斜柄＋開口圓頭，CSS 畫的）。
- **小程序後台第 24 個分頁「報修」**（STAFF／ADMIN／SUPER_ADMIN）：狀態 chips（待接單帶未處理數）、
  統計一行（平均處理時數、近 7 天新增）、熱門地點 chips、每列「接單」與「完成」（完成時 `wx.showModal` 收備註）。
- **網頁後台第 21 個分頁「報修」**：同一份資料，狀態／地點篩選、接單、完成（備註輸入框）、統計一行。
  兩套後台功能一致 —— 只補一邊等於沒做。
- 使用說明補四條：學生兩條（怎麼報、怎麼看進度）、校內職員一條（在哪裡接單與統計）、資訊管理員一條（熱門地點）。
- `docs/openapi.yaml` 補 8 個路徑／10 個操作 ＋ `Repair` schema。

## 抓到的問題（邊做邊修）

- **YAML plain scalar 不能含 ASCII 冒號**：`description: 沒有 repair:handle` 讓整份 `openapi.yaml` 被工具拒絕寫入，
  換成加引號才過 —— 與 v0.107.0 同一個坑，這次在寫入前就撞到。
- **`check-project` 抓到兩個新頁面的真問題**：`pages/repair/create` 的 `L: L` 不算「有 setData labels」
  （守門要求字面 `L: this.labels()`），以及七個設備名稱與四個地點字面值沒有包 `i18n.pick()`。
  兩者都是「簡體模式會半繁半簡」的成因，不是風格問題。
- **`check-states` 要求新頁面先登記三態**：兩個新頁面沒登記就紅燈，補上（表單頁標明「送出失敗用彈窗」）。

## 設計取捨

- **地點與設備是自由文字＋常用 chips，不建「課室表」**：學校的課室叫法每學年都在變（304／S304／高二忠課室），
  維護一份永遠落後的清單比讓使用者自己打更麻煩；統計用字串分組就夠。
- **照片先只收連結**：COS 直傳還沒接，與其讓使用者選了本機圖片卻上傳失敗，不如明講「只收 https 網址」。
- **老師沒有 `repair:handle`**：老師負責「發現並回報」，接單與結案是總務的行政流程；
  給老師接單會讓「誰修的」變成兩套紀錄。
- **完成可以由任何總務做（不限定原接單人）**：現實會交接班；`version` 與條件式更新仍保證不會重複完成。
- **不做「報修評分」**：修得好不好由總務與校方判斷，讓學生打分會變成另一條要維護的流程。
