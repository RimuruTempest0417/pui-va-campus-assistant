# v0.74.0 — 貼上去就通知「另一半」（W-57）

後端對應版本 **v0.35.0**。

## 做什麼

失物的智能配對（W-9）本來就會算「哪幾筆像」，但**只有打開某一筆詳情頁時才看得到**。
實際情境是這樣：同學 A 在圖書館丟了雨傘、貼了失物；三天後同學 B 撿到一把傘，貼了拾獲。
配對結果其實已經算得出來（同分類、地點相近、時間接近），但 **A 永遠不會知道** ——
他得自己想到「再去刷新一次失物列表」，而且還不一定翻得到那一筆。

這一版把配對從「被動等你看」變成「主動告訴你」：

- 貼出失物／拾獲的**當下**，後端立刻反查一次配對，對「另一半」的作者發一則**站內通知**。
- 通知的標題直接講人話：
  - 有人貼拾獲 → 失主收到「**有人撿到像你的「黑色雨傘」**」
  - 有人貼失物 → 撿到東西的人收到「**有人在找可能是你撿到的「黑色雨傘」**」
- 通知內文寫出**為什麼像**（同分類／地點相近／N 小時內／描述相似）與新紀錄的地點，
  點一則直接跳到那筆失物詳情，接著就能提出認領。
- 通知中心（首頁鈴鐺）多一種標籤「**失物**」（`kind = ITEM`），與活動／認領／公告分得開。
- 使用說明（學生分頁）新增一條問答：「別人撿到我的東西，我會知道嗎？」

## 四條刻意的規則

1. **一位作者只收一則**。同一個人可能貼了好幾筆相似的失物（「黑色雨傘」「黑色長柄雨傘」），
   逐筆通知就是騷擾。
2. **不通知自己貼的另一筆**。自己配到自己沒有任何資訊量。
3. **配對失敗不影響發文**。整段包在 `catch` 裡（只寫一筆 `warn`）：通知是加分項，
   貼文本身不能被它拖垮；建立仍然回 `201`。
4. **配對規則只有一份**。原本的 SQL＋閘門＋門檻全部搬進 `src/lib/item-match.ts`，
   `GET /items/:id/matches` 與建立後的主動通知都呼叫同一支 `findMatches` ——
   兩邊各抄一份的話，通知會推出「配對頁看不到」的配對，使用者會直接回報不一致。

## 設計取捨

- **不做「已讀就不再通知」之外的節流**：同一場配對本來就只會在新紀錄建立時觸發一次，
  再加上「一位作者一則」與「不通知自己」，不需要額外的時間窗去重。
- **不動資料表**：`Notification.kind` 本來就是 `String(32)`，加 `ITEM` 不需要 migration。
- **示範模式不假造通知**：mock 建立失物時不會憑空生一則「別人收到通知」——示範模式裡沒有其他真實使用者，
  假裝有才是騙人。改成在示範資料裡預放一則，讓畫面看得到樣式。

## 已知缺口

- 微信訂閱消息沒有加這條場景：配對通知只走站內（模板 id 需先在後台建立，且使用者要按過允許）。
- UI 只驗到資料與結構，**通知中心那顆「失物」標籤的觀感**沒有親眼看到；顏色刻意沿用中性灰
  （沒有新增色票，避免與活動的紫色標籤搶焦點）。
- 配對通知沒有「取消訂閱」開關：目前所有登入者都會收到，後續若要加開關，位置在設定頁的通知區。
