# v0.49.0 — 資源回收桶（W-40）

> 前端 **v0.49.0**｜後端 **v0.24.0**｜2026-10-25

## 做什麼

**公告以前是真的刪掉，現在只是「收起來」，後台看得到、可以還原。**

校內最常見的求救是「我剛剛把公告刪掉了」——舊版 `DELETE /admin/notices/:id` 直接 `prisma.notice.delete()`，刪完只剩重打一次。這一版把公告改成軟刪除，連同早就用軟刪除的失物，一起放進新的「垃圾桶」分頁。

- **後端**
  - `Notice` 加 `deletedAt`／`deletedBy`（`LostItem` 本來就有），migration `20261024221405_trash_soft_delete`。
  - `DELETE /admin/notices/:id` 改成寫 `deletedAt`＋`deletedBy`，回 `{ ok, softDeleted: true }`；重複刪除回 404（不產生第二筆紀錄）；已刪的公告也不能再 `PATCH`（先還原再改）。
  - **每一個公開公告查詢都掛 `deletedAt: null`**：`/notices` 列表、`/notices/:id`、`/notices/read-all`、後台公告清單、後台概況的「有效公告數」、家長端未讀計數、檢舉目標存在性。漏一個就會「後台刪了、首頁還在」。
  - 新 `GET /admin/trash?type=all|notice|item`：兩張表的下架紀錄合成一份，依刪除時間新到舊，帶 `counts{notice,item,all}`。
    - 「誰刪的」：公告讀自己的 `deletedBy`；**失物沒有這個欄位（早期就加的），從審計紀錄 `item.remove` 的操作者回推** —— 兩邊回同一個欄位 `deletedByName`，前端不用分支。
  - 新 `POST /admin/trash/restore {type,id}`：把 `deletedAt` 清掉並寫審計 `trash.restore`。**「不存在」與「本來就沒刪」都回 404**，不給回收桶當探測工具。
  - 新能力 `trash:manage`（ADMIN 以上）。老師／職員都不給：還原公告等於把撤下的內容重新公開，屬管理員職責。
  - 回收桶只做還原，**刻意不做永久刪除**（見下）。
- **小程序後台**：新增「垃圾桶」分頁（`ADMIN`／`SUPER_ADMIN`），類型 chips（全部／公告／失物）＋筆數摘要＋每列「內容／類型／刪除時間／誰刪的」＋還原（二次確認，因為還原等於重新公開）。
- **網頁後台**：同一個功能（`GET /admin` 的「垃圾桶」分頁），同一支端點、同一組欄位 —— 兩套介面同步是硬規則。
- `docs/openapi.yaml` 補兩支契約（共 94 路徑／110 操作）。

## 怎麼驗

- 後端 `npm test`：**27 檔 254 項全綠**，新增 `tests/e2e/trash.test.ts` 6 項：
  1. 刪除是軟刪除：公開列表與詳情看不到、後台公告清單沒有、**資料庫那列還在且 `deletedAt` 有值**、`deletedBy` 是操作者、已刪不能再 `PATCH`、重複刪除 404。
  2. 垃圾桶看得到（含「誰刪的」＝資訊管理員）→ 還原 → 公開列表與詳情回來、垃圾桶清空、`deletedAt` 歸 null、審計留下 `notice.delete` ＋ `trash.restore`。
  3. 失物下架 → 進垃圾桶、`deletedByName` 由審計回推、`type=notice` 不會混進失物 → 還原後 `GET /items` 可見。
  4. 沒被刪的與不存在的都回同一個 404、參數缺漏 422。
  5. 老師／學生 403、未登入 401（清單與還原兩支都驗）。
  6. 已刪的公告不算進後台概況的「有效公告數」。

## 抓到的 bug／要注意的地方

- **`admin-extra.test.ts` 有一條斷言編碼舊政策**（`expect(prisma.notice.count()).toBe(0)`）。改成軟刪除後它變紅 —— 這是政策變更的預期結果，已在同一版改成「列還在但 `deletedAt` 有值、對外 404」，並在測試裡寫明原因，避免之後有人把它「修回去」。
- 「誰刪的」對失物只能回推審計紀錄，所以**早期沒有寫審計的下架紀錄會顯示「（未記錄）」**，不會亂猜。
- `i18n-phrases.js` 重新產生（789 組，42.9 KB → 43.9 KB）：新增 12 條文案，沒有出現檔案翻倍的老問題。

## 設計取捨

- **不做永久刪除**。軟刪除的列不佔什麼空間；硬刪要處理認領／已讀／檢舉／訂閱的 FK 連鎖，而「回收桶」真正要解決的是「救得回來」，不是「清得乾淨」。想要真的清空，走備份／維運腳本，不要在半夜從後台按。
- **不另開 `trash` 表**。另開表等於同一筆資料存兩個地方，還原時要處理「垃圾桶有一筆、原表沒有」的漂移；現在垃圾桶只是兩張表 `deletedAt != null` 的視圖。
- **活動不進垃圾桶**：活動沒有刪除操作（只有 DRAFT／PUBLISHED／CANCELLED／FINISHED 狀態），沒有東西要還原。
